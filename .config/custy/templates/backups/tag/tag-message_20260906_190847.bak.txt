🚧 Reflow v1.0.0-rc.1 — Release Workflow Toolkit Release Candidate

Reflow v1.0.0-rc.1 is the first release candidate for the 1.0 release line. It
consolidates the large set of changes developed after v0.1.0 and is intended
for users, release engineers, and contributors who want to validate the new
repository targeting, version conversion, release recovery, Docker workflows,
and developer foundation before the stable v1.0.0 release.

Reflow has evolved from a small CLI that implicitly operated on the current
directory into a structured release-workflow toolkit. Commands now identify
their target repository, consequential changes are previewed or require
explicit opt-in, and the internals are divided into focused components that are
easier to understand, test, debug, maintain, and extend.

### 🌟 Highlights

- A clearer Typer and Rich CLI centered on `reflow init`, scoped local or remote tag conversion, `reflow releases recover`, and `reflow dockerize`.
- Local repository targeting with `--repository`, `--repo`, or `-C`.
- Direct GitHub or GitLab repository URL targeting with `--repository-url` and managed temporary clones.
- Bidirectional PEP 440 ↔ SemVer tag conversion, with SemVer as the default destination.
- Conversion previews that show the selected repository, every planned mapping, skipped-tag reasons, and the requested local or remote effects.
- Confirmation before live tag conversion and release recovery, with `--yes`/`-y` for reviewed automation.
- All-or-nothing local tag-reference transactions and guarded atomic remote replacements selected through explicit `local` or `remote` subcommands.
- GitHub release recovery that finds version tags without a corresponding GitHub Release and re-pushes them to retrigger existing tag-based CI/CD.
- Docker image build and publishing workflows for GHCR, GitLab Container Registry, or both.
- Clear Docker failure summaries with affected image tags, actionable reasons, partial-publication counts, and reliable nonzero exit status.
- Consistent dry-run simulation across conversion, recovery, Docker, and initialization workflows.
- Configurable remote-clone spinners, conversion-stage progress, release-recovery counters, Docker publishing progress, and initialization activity.
- Concise command errors without normal-mode Python tracebacks, with deeper diagnostics retained for `--debug` and log inspection.
- Expanded automated tests, MkDocs documentation, Q&A, troubleshooting, architecture diagrams, CI/CD, Docker Compose, and modular Make workflows.
- Hardened GitHub and GitLab delivery: temporary repositories use their own registry namespace, production requires a non-empty annotated tag, RC images keep their exact version without replacing `latest`, and the full tag message becomes a safely rendered provider release description with populated metadata and literal Docker commands.
- Private GitLab PyPI delivery for the `git-reflow` distribution, with
  `v1.0.0-rc.1` published as canonical package version `1.0.0rc1` only after
  the protected release pipeline passes.

### 📦 Install the private RC package

Authorized GitLab users can install the RC from the project's private package
registry. Configure pip authentication using a deploy token limited to
`read_package_registry`, then use the token-free project index URL:

```bash
python -m pip install \
  --index-url "https://gitlab.com/api/v4/projects/<project-id>/packages/pypi/simple" \
  "git-reflow==1.0.0rc1"
```

Supply the deploy-token username and token through pip's protected credential
mechanism or its interactive prompt—never in committed configuration or shared
command history. The distribution name is `git-reflow`; the installed command
remains `reflow`. Unprotected tags validate the same artifacts but cannot
publish them.

### 💻 Better for Reflow users

- The active local path or remote URL is displayed before operational work begins.
- A target can be selected once in `[tool.reflow.repository]` or overridden for one command from the CLI.
- URL targets are cloned into a temporary checkout and removed after the command. This supports remote conversion, release recovery, and Docker workflows; `reflow init` and `tags convert local` still require a persistent checkout.
- `reflow tags convert local` changes only a persistent checkout; `reflow tags convert remote` changes only its selected Git remote through one guarded atomic push.
- Both scopes convert PEP 440 tags to SemVer by default or SemVer tags to PEP 440 with `--to pep440`.
- Successful conversion replaces each source name in the selected scope, preserves supported lightweight or annotated metadata, and does not leave additive duplicate names.
- `reflow releases recover` explains its remote tag changes and asks for confirmation before it deletes and re-pushes selected tags.
- `reflow dockerize` shows the target repository, provider, and image destinations before it builds or publishes images.
- Global `--dry-run`, `--debug`, `--log-level`, and `--no-banner` controls improve safety and troubleshooting.
- `[tool.reflow.cli.progress].enabled` can hide animation in CI logs without changing work, safety checks, or dry-run behavior.

### 🛟 What release recovery means

`reflow releases recover`:

1. Reads existing version tags from the selected repository.
2. Checks which tags do not have corresponding GitHub Releases.
3. Deletes and re-pushes those selected remote tags.
4. Retriggers the repository's tag-based CI/CD release automation.

It does not directly create a release through the GitHub website. The target
repository must already have a workflow that creates a release in response to
a tag push. GitLab release discovery and recovery are not implemented in this
release candidate.

The former `reflow tags replay` command remains available only as a deprecated
compatibility alias. New commands and automation should use
`reflow releases recover`.

### 🔀 Safer version conversion

Conversion now starts with a collision-aware plan. Reflow skips tags that
already match the destination format or cannot be parsed, and stops the
complete plan when an existing destination would collide. Signed tags are
rejected because renaming would invalidate their signatures. Replacement tags
retain lightweight targets or supported annotated metadata, including the
target, tagger identity and timestamp, timezone, message, and encoding header.

The defaults are intentionally conservative:

- Destination format: SemVer
- Scope: explicit `local` or `remote` subcommand
- Replacement: atomic within the selected scope
- Confirmation for live changes: yes

Use `--yes` only after reviewing the displayed plan. The local command never
pushes, while the remote command intrinsically performs its guarded atomic
replacement. Arbitrary custom tag formats are not inferred in this release.

### 🧰 Better for contributors and integrators

- CLI commands, options, models, resolvers, help text, and presentation are separated from domain workflows.
- Git, GitHub, Docker, repository, initialization, dry-run, and task-execution responsibilities have focused services and executors.
- Protocols, factories, typed targets, shared results, and domain exceptions provide clearer extension and testing boundaries.
- Reusable UI and theme components keep terminal output consistent.
- Modular Make targets cover setup, local commands, tests, linting, QA, CI, docs, builds, Docker, Compose, remote images, Git helpers, and cleanup.
- The expanded test and documentation structure makes regressions and project behavior easier to locate and review.

### ⚠️ Upgrade notes for v0.1.0 users

- Python 3.14 or newer is required.
- Replace `.reflow.toml` with `.config/reflow/config.toml` and review the new `[tool.reflow.*]` schema.
- Replace `reflow convert-tags` with `reflow tags convert local` or `reflow tags convert remote` according to the intended persistence scope.
- Replace `reflow replay-tags` with `reflow releases recover`.
- Remove legacy `--push` and `--delete-old` usage; choose the explicit local or remote conversion subcommand instead.
- Review `[tool.reflow.repository]`, `[tool.reflow.git]`, conversion, recovery, Docker, registry, and logging settings before live use.
- Update scripts for the new command hierarchy and place global options before the command group.
- Run command-specific `--help` output before migrating existing automation.

### 🧪 Recommended RC validation

Please validate this release candidate in a disposable or non-production
repository first:

1. Install Reflow v1.0.0-rc.1 in an isolated Python 3.14 environment.
2. Run `reflow init` in a local test project and review the generated configuration.
3. Select the intended checkout with `-C`/`--repository`, or use `--repository-url` for a temporary clone.
4. Preview local conversion with `reflow -C <path> --dry-run tags convert local`.
5. Preview remote conversion with `reflow -C <path> --dry-run tags convert remote`.
6. Verify both directions with the default SemVer plan and `--to pep440` where relevant.
7. Preview recovery with `reflow -C <path> --dry-run releases recover`.
8. Preview container work with `reflow -C <path> --dry-run dockerize`.
9. Confirm the displayed repository, conversion scope, tag mappings, registry provider, and image names before allowing side effects.
10. Report migration problems, unsafe behavior, or unexpected output before v1.0.0 is promoted.

### 🚧 Release-candidate status

The Reflow 1.0 work was recorded across four untagged development checkpoints:
checkpoint 1 established the redesigned product foundation and general CI/CD,
build, quality, testing, and documentation hardening; checkpoint 2 added private
GitLab package delivery and its publication safeguards; and checkpoint 3 added
optional repository-metadata maintenance. Checkpoint 4 corrected GitHub Release
rendering so metadata and Docker instructions remain clean and literal. This RC.1
tag promotes the cumulative, reviewed result; it is not a fifth implementation
checkpoint.

- This is a pre-release and is not yet the final stable release.
- Release recovery currently supports GitHub release discovery; GitLab release recovery remains future work.
- Custom version formats beyond the supported PEP 440 and SemVer conversions remain future work.
- The stable v1.0.0 release may include final cleanup, documentation corrections, migration refinements, and fixes discovered during RC validation.

Thank you for testing Reflow 1.0 and helping validate the new release-workflow
foundation before its stable release.
