✅ Reflow v1.0.0 — Stable Release Workflow Toolkit

Reflow v1.0.0 promotes the release-workflow foundation reviewed in
`v1.0.0-rc.1` to the first stable 1.0 release line.

Reflow 1.0 evolves the project from a small, current-directory-oriented Git
automation script into a structured toolkit for repository-aware version-tag
conversion, GitHub release recovery, and Docker image publishing. The stable
release combines clearer user workflows and safer mutation controls with an
internal architecture that is easier for contributors to understand, test,
debug, maintain, and extend.

### 🌟 Highlights

- Focused `reflow init`, `reflow tags convert local`, `reflow tags convert remote`, `reflow releases recover`, and `reflow dockerize` commands.
- Rich help, repository details, conversion plans, configurable progress displays, confirmations, summaries, and actionable failures.
- Existing local checkout targeting with `--repository`, `--repo`, or `-C`.
- Direct Git repository URL targeting through temporary, automatically cleaned clones.
- Bidirectional PEP 440 ↔ SemVer conversion with SemVer as the default destination.
- Collision-aware, all-or-nothing tag replacement that preserves lightweight targets and supported annotated-tag metadata.
- Explicit local or remote conversion scope plus `--yes` for reviewed live operations.
- GitHub release recovery by re-pushing tags that lack corresponding GitHub Releases and retriggering existing tag-based CI/CD.
- GHCR and GitLab Container Registry image workflows driven by the selected repository's tags and build context.
- Actionable per-image Docker failure summaries, partial-publication reporting, and reliable command exit codes without normal-mode Python tracebacks.
- Consistent dry-run behavior that keeps useful discovery while simulating persistent local, remote, and Docker mutations.
- Namespaced `.config/reflow/config.toml` configuration with CLI → configuration → default resolution.
- Actionable repository-target configuration errors, nested help that remains available during repair, and Windows-safe progress output.
- Expanded automated tests, user and developer documentation, Q&A, troubleshooting, architecture diagrams, modular Make targets, Docker Compose, packaging, and CI/CD automation.
- GitHub and GitLab release safeguards that derive registry destinations from the active repository, require reviewed annotated tags, preserve safely rendered full tag-message release notes with populated metadata and literal Docker commands, publish exact prerelease images, and publish stable images under exact, minor, major, and `latest` tags.

### 💻 For Reflow users

- Configure one target under `[tool.reflow.repository]`, or override it for a single command with a local path or repository URL.
- Use `--dry-run` before conversion, release recovery, or Docker publishing and verify the displayed target and planned effects.
- Use `reflow tags convert local` for a local reference transaction and `reflow tags convert remote` for a guarded atomic remote replacement.
- Expect a successful conversion to replace source names only in the selected scope rather than creating additive duplicate names.
- Review collision and signed-tag failures before retrying; Reflow does not partially apply a blocked plan.
- Use `--to pep440` when converting supported SemVer tags in the reverse direction.
- Use `reflow releases recover` only when the repository already has tag-based release automation that should be retriggered.
- Keep repository selection and Docker image destination configuration separate and verify both before publishing.
- Keep `[tool.reflow.cli.progress].enabled = true` for interactive feedback, or set it to `false` for quiet CI presentation without changing execution behavior.

### 🛟 Release recovery scope

Release recovery reads existing version tags, checks for missing GitHub
Releases, deletes and re-pushes the selected remote tags, and thereby retriggers
the repository's existing CI/CD workflow. It does not create a GitHub Release
directly. GitLab release discovery and recovery are not included in v1.0.0.

The former `reflow tags replay` spelling remains available as a deprecated
compatibility alias. Use `reflow releases recover` in new documentation,
scripts, and automation.

### ⚠️ Upgrade notes for v0.1.0 users

- Python 3.14 or newer is required.
- Migrate `.reflow.toml` settings to `.config/reflow/config.toml` and its `[tool.reflow.*]` sections.
- Replace `reflow convert-tags` with `reflow tags convert local` or `reflow tags convert remote` according to the intended scope.
- Replace `reflow replay-tags` with `reflow releases recover`.
- Remove legacy `--push` and `--delete-old` options from automation and choose the explicit local or remote conversion subcommand.
- Configure or pass the intended repository target explicitly when Reflow is invoked outside that project.
- Preview all consequential workflows with `--dry-run` before allowing live changes.
- Review `reflow --help` and command-specific help before migrating scripts.

### 📦 Private GitLab installation

Authorized users can install the stable Python package from the project's
private GitLab PyPI registry. Configure pip authentication with a deploy token
limited to `read_package_registry`, then use the token-free project index:

```bash
python -m pip install \
  --index-url "https://gitlab.com/api/v4/projects/<project-id>/packages/pypi/simple" \
  "git-reflow==1.0.0"
```

Supply credentials through pip's protected credential mechanism or interactive
prompt. The package name is `git-reflow`, while the command remains `reflow`;
never commit a token or credential-bearing package-index URL.
